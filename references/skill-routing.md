# 诊断、TDD和评审的衔接

本技能管范围、版本、证据和交付；专门方法按任务选择。先发现并读取当前环境中的实际技能，不假定同名技能的版本、路径或要求一致。可选技能缺失时说明，仍可按当前授权做普通分析，不冒称使用了它。

| 需求 | 组合方式 |
|---|---|
| 已有异常但根因不清 | 证据/对象核验→诊断反馈循环→原因验证→最小修复 |
| 新能力且接口行为明确 | 验收/before基线→适用的TDD→回归/交付 |
| 原因与修复方式明确 | 最小补丁及相关回归，无需重新虚构诊断故事 |
| 只核数据/归档/回退 | 证据或恢复流程，不强行启动诊断/TDD |
| 评审未提交变更 | 实际before/after差异与需求核对，不能用空分支diff报通过 |

## 诊断

优先建立确实执行到目标路径、能捕获用户原症状的反馈循环。编译错误、空跑或另一种失败不算原缺陷复现。比较候选预测，按判别力选择实验；不能凭第一种听起来合理的解释直接改生产。

若无设备、需人工部署或长时间采集，记录尝试与缺口，按当前用户授权决定可否继续源码、原始日志及隔离实验的受限分析。专门技能有前置门槛时必须读取并遵守；需要适配且尚未获得授权时，说明具体规则与影响。已有明确授权不重复询问，不能靠改名绕过。

受限分析按证据列候选，不编造数量。候选、静态风险、主机机制验证、目标环境验证分别标注；授权分析不等于授权猜测改生产。满足证据且处于已有修复范围时可落地，缺少的实机回归如实保留。

## TDD

通过公开可观察边界验证行为。先核接口、输入、输出及失败处理；用户已明确的沿用，用户已授权代理选择边界的，在明确需求内说明后继续。若实际TDD技能要求确认而当前授权未覆盖，先给具体接口与行为例子再问。不要让技能安装本身冒充用户授权。

每次一个纵向切片：观察真实行为失败→最小实现→验证。预期来自独立需求或手算样例，不复写实现公式。边界不清时先澄清设计，不先堆想象接口的测试。公司小版本不能为测试便利重构架构、暴露内部实现或新增无关依赖。

## 评审与清理

核实际评审工具的比较范围、固定点及配置要求。分支三点diff可能漏掉全部未提交改动；不为满足评审工具而提交公司库或新增无关配置。适用条件不匹配时，按授权使用真实before/after普通评审，并准确说明使用方式。

评审阶段不自动授权重构。按来源和用途清理本任务临时插桩，保留公司基线日志/debug/历史分支、实际工程用户改动、失败证据及用户要求的测试工程。纯产品候选只迁必要修复，不带历轮专用实验或无关差异。
