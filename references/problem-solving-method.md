# 可迁移的探索方法：如何找到下一步

用于新目标、疑难故障、性能与实验设计。只读解释和已明确的版本恢复不必走此循环。下列是从历史成功与失败提炼的方法，不声称历史每一步都预先设计了严格实验。

## 从目标推进，而不是从某个补丁出发

1. **定义成功。** 写用户可观察的行为、数据规模、失败处理和不可牺牲的约束。正确性、数量完整性、顺序、来源、时延、资源用量分别判断；不能用一个总数替代全部目标。
2. **做小而可信的基线。** 用可人工核对的小输入跑通真实路径，校验生成器/观察器/判据。先把仪器或检查器错判排除掉。新增能力从一个可用的端到端切片起步；已有故障优先建立真实反馈循环；受限实机按当前授权及实际技能要求处理，见技能衔接。
3. **有目的地放大。** 保留版本、规则和输入特征，只增加与疑问相关的一项：数量、持续时间、并发、负载、故障频率或输入边界。数量增大不等于速率增大；低负载通过不外推高负载可靠。
4. **拆开症状和层次。** 找第一处违背约定的边界。沿输入→转换→共享状态→调度/发布→外部输出→消费追踪，不只看最后报错。某处“成功”只证明该层的约定，不能自动跨到端到端成功。
5. **从残余异常提出新问题。** 一种错误消失而另一种仍在，保留已成立结果，给剩余问题新的观测点和候选解释。不要一边重复修已解决路径，一边把所有异常都归为同一个原因。
6. **需要时制造有判别力的条件。** 随机长测未命中时，用真实调用入口、受控调度、固定时钟/种子、故障注入或资源限制，让竞争解释给出不同结果。记录条件是否确实发生；没触发不是修复成功。
7. **固定判据比较干预。** 在同一测试器/输入和相关条件下比较旧/新实现，尽量只改一个机制；必要时反向撤回该机制复测。多项一起改只证明组合效果，不分摊各项贡献。用触发记录、输出和恢复进展共同证明效果。
8. **回原场景并收敛。** 定向条件支持一个机制，还要核原始场景和相关回归。满足明确验收即可交付；剩余未知写清楚，不无限增加无关实验，也不把“实验未复现”改写为“生产问题已消除”。

## 新思路从哪里来

| 线索 | 接下来问什么 | 能区分的动作 |
|---|---|---|
| 总数正确但内容/归属错误 | 数据在何时被另一请求替换，还是检查器分组错？ | 给操作独立身份，核共享对象写入/发布前后与原始输出 |
| 顺序改善但遗漏仍在 | 是否还有无人继续处理的工作、满队列失败或观察遗漏？ | 同时看提交/消费/完成/继续唤醒及日志丢弃，找计数首次分叉点 |
| 减速后成功 | 是资源容量、竞争概率，还是采集链承载能力敏感？ | 分别固定负载和观测方式改变节奏；不直接把减速当根治 |
| 两版都绿、理论危险窗口仍存在 | 测试有没有真正撞到该条件？ | 加触发与延迟交付证据，设计可控时序，再比较实现 |
| 错误总带特定位置/倍数/周期 | 是否边界、回绕、重用或过滤规则相关？ | 改边界附近输入与长度，检验现象是否按预测移动 |
| 结果随日志/测试器版本变化 | 观察代码是否丢事件、改变时序或放宽判据？ | 用手工可核样例和故意损坏输入检查判据，重测同版产品 |
| 多个方案都说得通 | 哪个最小实验会让候选给不同预测？ | 按区分能力、成本和副作用选一个实验，不按模型语气选方案 |

探索候选可检查：边界/算法、所有权/生命周期、并发/发布、状态机/失败恢复、构建配置、外部依赖、观察链。只选与证据有关的方向。创新也可以是更好的观测点或更小的反例，不要求推翻现有架构。采用方案说明依据和可推翻条件；没有证据支持的想法保留为候选。

## 先检查判据有没有把事实挡掉

当统计为零、数量悬殊或结果随检查器变化时，先建立 **原始输入候选→解析成功/拒收原因→可信业务记录→内容有效→有效唯一数** 的统计链；保留被拒样本，不把它们直接算成“未到达”。对照规范、参考实现和真实字段，分别记录版本；有冲突时查兼容/需求依据，不因某份文档或某个实现就武断放宽判据。用已知正确与故意损坏样例核新旧判据，保留仍然需要的完整性和内容校验。候选被找回不等于正文已正确，也不能自动解释另一类重复或乱序。

相同输入可能让覆盖不可见：用可辨认的身份、来源与正文设计区分条件，核周期模式的碰撞盲区。测试条件改动按授权执行，旧新两版在共同规则下重比。

## 失败反馈怎样改正

| 实际反馈/曾踩的坑 | 改正方法与结论边界 |
|---|---|
| 旧版编译报错、检查器没启动，却当“红控” | 先修验证设施；只有执行到目标路径并出现预期缺陷，才是有效旧版失败 |
| 旧新都过但触发为零 | 改刺激/观察，不继续堆补丁；只说该条件未覆盖 |
| 旧新都失败 | 先比较失败签名；区分原缺陷未解决、新回归、输入或测试器错误 |
| 某项改善就宣布全部修好 | 每项验收单独记；剩余异常成为下一问题，不抹掉它，也不无证据推翻已成立项 |
| 为了变绿修改测试器或关闭故障刺激 | 留旧失败与规则diff；证明请求实际发生、保护期间阻挡、解锁后交付。修正测试器后用正确/错误样例核判据，让两版产品共同重测；刺激关闭的绿色不能证明原场景修复 |
| 重跑偶然成功覆盖失败轮 | 保存失败和所有有效尝试的分母，记录重跑原因；不能挑最好一轮证明稳定 |
| 总记录数齐便宣称无丢失 | 还查身份、唯一性、来源、完整内容；重复可能掩盖缺失，交叉类别不能简单相加 |
| 多轮各取最好证据拼成闭环 | 同轮才逐项对账；跨轮只比较现象，不伪造源码/运行/两端对应关系 |
| 复制两次同样漏目录仍称完整 | 枚举错误必须失败；核范围与全集、Git对象真实导出，不只核已复制文件 |
| 依据记忆/日志重写旧版本 | 查询确切Git commit、范围清单和实际导出；无法唯一定位就不猜，保留当前状态 |

关锁/关中断的成功至少区分**安全性**（内容不坏）、**进展性**（请求最终能完成）和相关时延。保护后没有命中可能是被正确阻挡，也可能是测试根本没请求，二者要用独立证据区分。

每次转向留一条短记录：**用户关键问题/原始观察 → 原假设与反证 → 为什么转向 → 新实验及实际结果 → 采用/放弃理由与结论边界**。链接原始出处与输入/实现/判据版本，区分用户原话、代理提炼、历史报告、原始工具输出及本轮实测；保留失败签名。局部修复、完整原因解释和全目标验收分别判断：顺序改善不替遗漏通过，追赶能力改善不替最初延迟原因得到解释。

## 两个迁移示例

**网页搜索偶尔显示旧关键词结果：** 单次查询基线→快速连续查询→区分旧结果、重复请求、加载不结束→通过实际页面/API边界控制响应先后→核请求身份和最终可见结果→同样时序验证修复，再查取消、失败、正常顺序。这里只示范方法；未读代码前不能断言根因，也不能把嵌入式的关中断机制照搬成网页方案。

**新增可重试的批量导入：** 先确认公开接口、重试是否幂等、部分失败怎样显示→一个小输入的纵向切片→逐步扩展数量、重试和取消场景→核用户可见结果与相关资源约束。使用TDD时按当前授权和实际技能要求确认或选择公开边界，一次一个失败测试和最小实现；新功能的红表示约定尚未实现，不是历史缺陷复现。

性能任务还需固定数据、环境、资源和指标；变快却更易出错不能判整体成功。技能使用顺序见 [技能衔接](skill-routing.md)。
